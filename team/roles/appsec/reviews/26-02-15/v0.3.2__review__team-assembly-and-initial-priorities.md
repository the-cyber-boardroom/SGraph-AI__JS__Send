## Brief Received

The file transfer engine brief defines a pluggable crypto adapter using AES-256-GCM, a transfer manifest containing encryption metadata (wrapped keys, IVs), and a pipeline invariant (compress -> encrypt -> upload).

## Security-Critical Elements Identified

### From the Brief

1. **Pipeline invariant**: compress -> encrypt -> upload. Violating this order means encrypted data won't compress (performance issue) and could leak patterns (security issue if compression happens after encryption on already-structured data).

2. **Transfer manifest contains sensitive metadata**:
   - `encryption_metadata.wrapped_key` — wrapped symmetric key
   - `encryption_metadata.iv` — initialisation vector
   - `encryption_metadata.algorithm` — encryption algorithm identifier
   - `file.content_hash` — hash of original file content (potential information leakage)
   - `file.name` — original file name (privacy concern depending on use case)

3. **Key wrapping scheme**: per-file random symmetric key, wrapped with passphrase-derived key. Standard approach but implementation details matter enormously.

4. **Multi-runtime crypto**: Web Crypto API in browser, `crypto` module in Node.js. Both must produce identical ciphertext format (IV prepended, GCM auth tag appended).

5. **Chunk checksums**: SHA-256 per chunk. Are these checksums of encrypted chunks or plaintext chunks? If plaintext, they leak information. Must be checksums of encrypted chunks.

## Initial Security Questions

| # | Question | Severity if Wrong | For Role |
|---|---|---|---|
| 1 | Are chunk checksums computed on encrypted data or plaintext? | High — plaintext checksums leak content patterns | Architect |
| 2 | Does `file.content_hash` appear in the manifest? If so, this is a fingerprint that identifies the file even without decryption | Medium — enables file identification | Architect |
| 3 | Does `file.name` appear in the manifest in cleartext? | Medium — leaks metadata | Architect |
| 4 | What key derivation function for passphrase -> wrapping key? PBKDF2 is minimum, Argon2 is preferred | High — weak KDF enables brute force | Architect |
| 5 | Is the IV in the manifest the same IV used for encryption? If exposed, combined with weak key derivation this could be exploitable | Medium — standard practice is to include IV, but document why | Architect |

## Security Requirements (for Dev and Architect)

These requirements should be incorporated into the adapter interfaces:

1. Chunk checksums MUST be computed on encrypted chunks, not plaintext
2. The crypto adapter MUST generate a fresh 12-byte IV per encryption operation via cryptographically secure random
3. The crypto adapter MUST produce ciphertext in format: IV (12 bytes) || ciphertext || GCM auth tag (16 bytes)
4. The key wrapping MUST use a standard algorithm (AES-KW or AES-GCM with a separate wrapping IV)
5. The passphrase-to-key derivation MUST use PBKDF2 with >= 600,000 iterations or Argon2id
6. The pipeline invariant (compress -> encrypt -> upload) MUST be enforced in code, not just documented
