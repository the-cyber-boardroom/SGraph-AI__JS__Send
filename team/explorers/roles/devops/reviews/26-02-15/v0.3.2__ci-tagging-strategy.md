# CI Tagging Strategy — SGraph Send JS

**Role:** DevOps
**Version:** v0.3.2
**Date:** 15/02/2026
**Based on:** `SGraph-AI__App__Send` CI tagging strategy (v0.3.3)
**Purpose:** CI/CD pipeline with automated Git tagging for the JavaScript transfer engine.

---

## Overview

SGraph Send JS uses **automated Git tagging** as part of its CI/CD pipeline, following the same pattern as the parent SGraph Send project. Every push to `dev` or `main` triggers a pipeline that runs tests, increments a Git tag, and optionally publishes to NPM.

Tags are never created manually — the CI pipeline is the sole authority for version tags.

---

## Architecture: Three-File Workflow

The CI system uses a **three-file pattern**: two branch-specific trigger pipelines delegate to one shared base pipeline.

```
.github/workflows/
├── ci-pipeline__dev.yml      # Trigger: push to dev
├── ci-pipeline__main.yml     # Trigger: push to main
└── ci-pipeline.yml           # Shared base pipeline (workflow_call)
```

### Key Differences by Branch

| Aspect | `dev` branch | `main` branch |
|--------|-------------|---------------|
| Release type | `minor` (patch bump) | `major` (minor bump) |
| Tag example | v0.2.15 → v0.2.16 | v0.2.16 → v0.3.0 |
| NPM publish | No | Yes |
| Trigger | Push to `dev` or manual | Push to `main` or manual |

## Adaptation from App Repo

The JS repo CI pipeline is adapted from the Python/App repo with these differences:

| Aspect | App Repo (Python) | JS Repo (JavaScript) |
|--------|-------------------|----------------------|
| Runtime | Python 3.12 | Node.js 20 + 22 |
| Tests | `pytest tests/unit/` | `npm test` |
| Package manager | pip + PyPI | npm + NPM registry |
| Publish | `pypi__publish` action | `npm publish --access public` |
| Deployment | Lambda deploy (Admin + User) | None (standalone NPM package) |
| Multi-version testing | Single Python version | Matrix: Node 20, 22 |
| AWS secrets | 10+ Lambda/AWS secrets | None needed (NPM_TOKEN only) |

### What We Kept

- Three-file workflow pattern
- `owasp-sbot/OSBot-GitHub-Actions` for tag increment
- Tests → Tag → Publish ordering
- `minor` for dev (patch bump), `major` for main (minor bump)
- Graceful degradation (missing NPM_TOKEN skips publish, doesn't fail)

### What We Dropped

- Lambda deployment jobs (no Lambda in this repo)
- AWS credential check job (no AWS deployment)
- Python-specific actions (pytest, pip, pypi)

### What We Added

- Node.js matrix testing (20, 22) — multi-version validation
- NPM publish step with `NODE_AUTH_TOKEN`

## Pipeline Execution Flow

```
                        ┌──────────────────────┐
                        │  Run Tests           │
                        │  Node 20 + Node 22   │
                        │  (parallel matrix)   │
                        └──────────┬───────────┘
                                   │
                        ┌──────────▼───────────┐
                        │  Increment Tag       │
                        │  (minor/major)       │
                        └──────────┬───────────┘
                                   │
                        ┌──────────▼───────────┐
                        │  Publish to NPM      │
                        │  (main only)         │
                        └──────────────────────┘
```

### Critical Ordering

1. **Tag increment happens AFTER tests pass** on ALL Node.js versions
2. **Tag increment happens BEFORE publish** — published package is always tagged
3. **NPM publish only on main** — dev pushes increment tag but don't publish

---

## Tag Increment Mechanism

Uses the same external action as the App repo:

```
owasp-sbot/OSBot-GitHub-Actions/.github/actions/git__increment-tag@dev
```

| `release_type` param | What it bumps | Pattern | Example |
|---------------------|---------------|---------|---------|
| `minor` | Third number (patch) | `v0.X.Y → v0.X.(Y+1)` | v0.2.15 → v0.2.16 |
| `major` | Second number (minor), resets third | `v0.X.Y → v0.(X+1).0` | v0.2.16 → v0.3.0 |
