Includes cost projection tables for various transfer volumes. |
| R-05 | **Compression Algorithms** (`05-compression-algorithms.md`) | v0.3.13 | **P2** | Dev | Benchmarks and evaluation of JS/WASM compression options for the compress-before-encrypt pipeline. Covers: CompressionStream API (native gzip, 0 KB bundle, ~100 MB/s), fflate (8 KB, ~150 MB/s, streaming, all runtimes), zstd-wasm (~300 KB WASM, ~200 MB/s, best ratio-to-speed), brotli-wasm (~680 KB, slow compression ~30 MB/s, fast decompression), LZ4 (~15 KB, ~400 MB/s, lowest ratio), Snappy. Security analysis of IV reuse risks and 2^32 chunk limit per key. |
| R-07 | **Cloud Providers Comparison** (`07-cloud-providers-comparison.md`) | v0.3.13 | **P2** | Architect | Comparison of AWS S3, Azure Blob Storage, Google Cloud Storage, Cloudflare R2, and Backblaze B2. Evaluates: upload mechanisms, max object sizes, presigned/SAS URL support, browser-direct upload, S3 API compatibility, JS SDK availability, and cost. Key finding: 3 of 5 providers (R2, B2, GCS via XML API) are S3-compatible -- one adapter covers four providers. Only Azure requires its own adapter. Cost analysis shows R2 is 95x cheaper than S3 per transfer due to zero egress fees. Recommendation: S3 adapter first with configurable endpoint. |
| R-08 | **WebRTC P2P Transfer** (`08-webrtc-p2p-transfer.md`) | v0.3.13 | **P2** | Architect | WebRTC data channels for browser-to-browser file transfer. Covers: data channel modes (reliable ordered for file transfer), max message size (16 KiB safe cross-browser), DTLS 1.2 built-in encryption, browser support matrix (all modern including Safari with TURN caveat), signalling server design (AWS API Gateway WebSocket recommended), NAT traversal (ICE/STUN/TURN, 70-85% direct success, ~99% with TURN), TURN provider comparison (Cloudflare Realtime at $0.05/GB recommended), performance benchmarks (1.5-30 MB/s browser, 135-213 MB/s native), library evaluation (PeerJS recommended, simple-peer unmaintained), chunking protocol with 32-byte headers and flow control via bufferedAmount, resumable transfer protocol, security analysis (double encryption acceptable, IP exposure mitigations). Recommendation: Phase 3 transport adapter, not Phase 1. |
| R-09 | **Lambda Streaming Responses** (`09-lambda-streaming-responses.md`) | v0.3.13 | **P3** | Architect / DevOps | Lambda payload constraints and streaming evaluation. Covers: current Lambda limits (6 MB request/response in BUFFERED mode), Lambda streaming (200 MB response limit, 2 MB/s bandwidth cap beyond 6 MB -- makes streaming impractical for files >20 MB), Mangum does NOT support streaming (would need Lambda Web Adapter migration), API Gateway alternatives comparison, CloudFront + Lambda Function URL combination. Key finding: for SGraph Send's zero-knowledge model, Lambda should never touch file data -- presigned URLs to S3 are cheaper, faster, and simpler. Lambda's role is state management, auth, and URL generation only. Small file optimisation: keep Lambda-through path for files <5 MB. Cost comparison shows presigned URLs are 5-10% cheaper at small scale and dramatically cheaper at scale (~$15.60/month vs ~$90/month for 1,000 transfers/day). |
| R-10 | **Content-Addressable Storage** (`10-content-addressable-storage.md`) | v0.3.13 | **P3** | Architect | CAS and delta upload feasibility for SGraph Send. Covers: CAS concepts (hash-based addressing, Merkle DAG), application to SGraph Send (upload resumption, within-transfer dedup, delta uploads of modified files), chunking strategies (fixed-size vs. content-defined chunking/CDC using Buzhash or FastCDC rolling hash), delta upload mechanism (implicit via CAS -- only upload chunks with new hashes), storage layout design (chunks/{hash_prefix}/{hash} with 2-char hex prefix for S3 partition distribution), security analysis (CAS is safe because encryption uses random keys -- no convergent encryption, no cross-transfer hash correlation), implementation plans for client-side (Web Crypto SHA-256) and server-side (Python), garbage collection (mark-and-sweep recommended, deferred to Villager), performance analysis (400 ms CAS overhead vs. potential minutes saved on re-uploads). References restic, Borg, Git, IPFS. Recommendation: start with hash-based storage keys in Phase 1, fixed-size chunks, defer CDC and GC. |

#### MUST Read

| Doc | Why |
|-----|-----|
| **R-06** (Chunked Encryption) | The core security design. AppSec must verify: IV strategy (counter-derived, no reuse), AAD binding (prevents chunk reordering), key wrapping (PBKDF2 >=600K or Argon2id), GCM tag verification, and the 2^32 chunk limit per key. |
| **A-2** (Transfer Manifest Schema) | AppSec must audit: what information leaks through the manifest (file sizes, chunk counts, timing), that no plaintext or keys appear in the manifest, that chunk checksums are on ciphertext not plaintext, that IP addresses are hashed. |

## 4. Key Architecture Decisions

The 12 architecture decisions from A-3 (comparison-matrix.md), summarised here for quick reference.

| # | Decision | Choice | Rationale |
|---|----------|--------|-----------|
| **AD-1** | Upload library | Build from scratch | No existing library satisfies more than 3 of 7 hard requirements (encryption pipeline, multi-runtime, presigned URLs, 3-level progress, pause/resume/cancel, pluggable transport, transfer manifest). Borrow patterns from tus-js-client (retry backoff, httpStack) and Uppy (S3 multipart plugin API). |
| **AD-2** | Primary storage backend | AWS S3 via presigned URLs | Existing infrastructure. S3 adapter covers 4 providers (S3, R2, B2, GCS via XML API) with configurable endpoint. |
| **AD-3** | Cost optimisation path | Cloudflare R2 (config change only) | R2 is 95x cheaper per transfer than S3 due to zero egress fees. Same S3 API -- switch via endpoint configuration, no code change. |
| **AD-4** | Default compression | CompressionStream API (gzip) | Zero dependencies, native in all modern browsers and Node.js. Adequate compression ratio for most files. |
| **AD-5** | Compression upgrade path | fflate (8 KB) then zstd-wasm (300 KB) | Progressive enhancement. fflate adds compression level control. zstd-wasm offers best ratio-to-speed for large files on slow connections. |
| **AD-6** | Browser storage | OPFS (binary data) + IndexedDB (metadata) | OPFS is 2-7x faster than IndexedDB for large binary data with random access. IndexedDB is universal and ideal for structured metadata. Dual-storage with IndexedDB fallback. |
| **AD-7** | Encryption strategy | Per-chunk AES-256-GCM, counter-derived IVs, AAD binding | Enables independent chunk processing, parallel encryption, resumable uploads, and prevents chunk reordering/substitution attacks. Same key per transfer, deterministic IVs from chunk index. |
| **AD-8** | Upload transport | Browser direct to S3 via presigned URLs, bypassing Lambda | Eliminates Lambda's 6 MB payload limit. Lambda only generates URLs and manages state. No Lambda in the data path. |
| **AD-9** | Download transport | S3/CloudFront signed URLs | No Lambda payload limits. Cheapest path (egress only, no Lambda compute). CloudFront adds CDN caching and lower egress costs at volume. |
| **AD-10** | P2P transfer | Phase 3 -- WebRTC with S3 fallback | WebRTC is an optimisation (zero server bandwidth cost when both parties online), not a foundation. S3 is simpler, faster, more reliable, and works when parties are offline. |
| **AD-11** | Multi-runtime strategy | Pure JS core, platform-specific adapters injected | Core engine has zero platform-specific imports. Adapters for Storage, Crypto, Compression, Transport, Cache, Progress, ManifestStore are injected at construction. Test in Node.js first -- by the time code runs in a browser, it already works. |
| **AD-12** | Transfer state model | Transfer manifest as single source of truth | JSON document stored server-side, readable by both uploader and downloader. Enables resume, progress visibility from both sides, integrity verification, streaming download, retry tracking, and transfer history. |
