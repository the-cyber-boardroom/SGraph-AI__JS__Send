## 1. Architecture Decisions for Phase 1

### AD-1: Build the Transfer Engine from Scratch

**Decision:** Build the core transfer engine from scratch. Do not adopt tus-js-client, Uppy, Resumable.js, Flow.js, or any existing upload library as a dependency.

**Rationale:** No existing library satisfies more than 3 of our 7 hard requirements (client-side encryption pipeline, multi-runtime support, direct-to-S3 via presigned URLs, three-level progress events, pause/resume/cancel, pluggable transport, transfer manifest). The combination of compress-then-encrypt pipeline, multi-runtime targets (browser, Node.js, Deno, Bun), and the manifest-as-source-of-truth concept is unique to our use case. Wrapping an existing library would produce more adapter code than library usage.

**Borrow from existing libraries:**

| Concept | Source | What to adopt |
|---------|--------|---------------|
| Retry backoff array | tus-js-client | `retryBackoff: [0, 1000, 3000, 5000]` -- array index = attempt, value = delay ms |
| `onBeforeRequest` / `onAfterResponse` hooks | tus-js-client | Middleware pattern for transport-level interception |
| `shouldUseMultipart(file)` threshold | Uppy `@uppy/aws-s3` | Files < 5 MB use single PUT; files >= 5 MB use multipart |
| S3 multipart function interface | Uppy `@uppy/aws-s3` | `createMultipartUpload()` / `signPart()` / `completeMultipartUpload()` |
| Content fingerprinting for resume | tus-js-client | SHA-256 hash of first 1 MB + file size + file name for upload deduplication |

**Evidence:** Research document 02 (tus/Uppy evaluation), comparison matrix.

### AD-2: S3-Compatible Storage via Presigned URLs

**Decision:** Use AWS S3 as the primary storage backend, accessed exclusively through presigned URLs for both upload and download. Lambda generates URLs and manages state only -- Lambda never touches file data.

**Rationale:** The Lambda payload hard limit is 6 MB (request and response). Presigned URLs bypass Lambda entirely for data transfer, eliminating size limits and reducing Lambda execution cost to ~100 ms per URL generation call. A single S3 adapter (using `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner`) covers AWS S3, Cloudflare R2, Backblaze B2, and GCS (S3-compatible XML API) -- 4 of 5 major cloud providers.

**Configuration:**

```javascript
{
    bucket:           'sgraph-send-transfers',
    region:           'us-east-1',
    endpoint:         undefined,         // Set for R2/B2/MinIO
    forcePathStyle:   false,             // Set true for MinIO
    urlExpiry:        3600,              // Presigned URL lifetime (seconds)
    prefix:           'transfers',       // S3 key prefix
    hashDistribution: true,              // Hash-prefix for rate limit avoidance
}
```

**S3 key structure:** `transfers/{transfer_id[0:2]}/{transfer_id}/chunks/{chunk_index}` -- provides 256 hash prefixes (hex 00-ff) supporting up to 896,000 PUT requests/second across prefixes.

**Evidence:** Research documents 01 (S3 multipart), 04 (S3 constraints), 09 (Lambda streaming -- recommends presigned URLs over Lambda streaming).

### AD-3: 4 MB Default Chunk Size with Dynamic Sizing

**Decision:** Use 4 MB as the default chunk size. Implement dynamic chunk sizing for large files to stay within S3's 10,000-part limit.

**Rationale:** 4 MB provides a good balance between resume granularity (only 4 MB lost on retry), memory usage (two chunks in memory = ~8 MB for encrypt in/out), request overhead, and the 28-byte per-chunk encryption overhead (0.0007% at 4 MB). S3's minimum part size is 5 MB, but our chunks are encrypted with 28 bytes overhead per chunk, making the actual uploaded size ~4 MB + 28 bytes, which exceeds 5 MB when we include the overhead in the storage key calculation. **Important:** for S3 multipart uploads, the minimum part size is 5 MB. When using S3 multipart (not individual PUTs per chunk), the chunk size must be >= 5 MB. The engine must enforce `Math.max(chunkSize, 5 * 1024 * 1024)` when S3 multipart is the upload mode.

**Dynamic sizing algorithm:**

```javascript
function calculateChunkSize(fileSize, defaultChunkSize = 4 * 1024 * 1024) {
    const MAX_PARTS = 10000;
    const MIN_S3_PART = 5 * 1024 * 1024; // 5 MB S3 minimum

    let chunkSize = defaultChunkSize;

    // Ensure we don't exceed 10,000 parts
    if (fileSize / chunkSize > MAX_PARTS) {
        chunkSize = Math.ceil(fileSize / MAX_PARTS);
    }

    // Ensure S3 minimum part size (when using multipart)
    chunkSize = Math.max(chunkSize, MIN_S3_PART);

    return chunkSize;
}
```

**Evidence:** Research document 04 (chunk size analysis table), architecture recommendations.

### AD-4: Per-Chunk AES-256-GCM with Counter-Derived IVs and AAD

**Decision:** Encrypt each chunk independently using AES-256-GCM with counter-derived IVs and Additional Authenticated Data (AAD). Use `crypto.subtle` (Web Crypto API) as the single implementation across all runtimes.

**IV strategy:** Counter-derived. First 8 bytes are random (generated once per transfer as the `baseIV`). Last 4 bytes are the chunk index in big-endian. This guarantees IV uniqueness by construction (no birthday bound concern) and is deterministic (same chunk index always produces the same IV).

```javascript
function deriveIV(baseIV, chunkIndex) {
    const iv = new Uint8Array(12);
    iv.set(baseIV.subarray(0, 8));  // 8 random bytes (per-transfer)
    const view = new DataView(iv.buffer);
    view.setUint32(8, chunkIndex, false); // big-endian chunk index
    return iv;
}
```

**AAD structure:** JSON-encoded object binding each chunk to its position and transfer, preventing reordering, deletion, duplication, and cross-transfer replay attacks.

```javascript
function buildAAD(context) {
    return new TextEncoder().encode(JSON.stringify({
        chunk_index:  context.chunkIndex,
        total_chunks: context.totalChunks,
        transfer_id:  context.transferId,
    }));
}
```

**Per-chunk overhead:** 28 bytes (12-byte IV + 16-byte GCM auth tag). At 4 MB chunk size, this is 0.0007% overhead.

**Performance:** AES-256-GCM is hardware-accelerated via AES-NI on modern CPUs. Typical throughput: 1-4 GB/s in browsers, 2-6 GB/s in Node.js. Encryption is not the bottleneck; network I/O dominates.

**Multi-runtime compatibility:** `globalThis.crypto.subtle` is available in all target runtimes (browsers, Node.js 19+, Deno, Bun, Cloudflare Workers). For Node.js 15-18: `(await import('node:crypto')).webcrypto.subtle`.

**Evidence:** Research document 06 (chunked encryption patterns), adapter-interfaces architecture document.

### AD-5: Transfer Manifest as Single Source of Truth

**Decision:** Every transfer is governed by a transfer manifest -- a JSON document (schema version 1) stored server-side that tracks the complete state of the transfer. The manifest is the single source of truth for upload progress, download progress, resume capability, integrity verification, and streaming mode.

**Manifest schema (Phase 1 fields):**

```json
{
    "$schema": "transfer-manifest-v1",
    "version": 1,
    "transfer_id": "a1b2c3d4e5f6",
    "status": "uploading",
    "created_at": "2026-02-16T10:00:00.000Z",
    "updated_at": "2026-02-16T10:00:05.000Z",

    "file": {
        "name": null,
        "size_original": 15728640,
        "size_compressed": null,
        "size_encrypted": null,
        "content_hash": "sha256:a3f7b2c1...",
        "compression": "none",
        "encryption": "aes-256-gcm",
        "content_type_hint": "application/pdf"
    },

    "chunks": {
        "total": 4,
        "chunk_size": 4194304,
        "last_chunk_size": 3145728,
        "completed": [0, 1],
        "pending": [2, 3],
        "failed": [],
        "checksums": {
            "0": "sha256:abcdef...",
            "1": "sha256:123456..."
        }
    },

    "storage": {
        "mode": "chunked",
        "backend": "s3",
        "bucket": "sgraph-send-transfers",
        "prefix": "transfers/a1/a1b2c3d4e5f6",
        "upload_id": "s3-multipart-upload-id"
    },

    "timing": {
        "upload_started_at": null,
        "upload_completed_at": null,
        "chunks_per_second": 0,
        "estimated_completion_at": null,
        "total_bytes_uploaded": 8388608,
        "total_bytes_downloaded": 0
    },

    "encryption_metadata": {
        "algorithm": "aes-256-gcm",
        "chunk_iv_strategy": "counter-derived",
        "base_iv": "base64:...",
        "aad_fields": ["chunk_index", "total_chunks", "transfer_id"],
        "key_wrapping": "url-encoded"
    },

    "events": [],

    "download": {
        "count": 0,
        "first_download_at": null,
        "last_download_at": null
    }
}
```

**Status lifecycle:** `pending` -> `uploading` -> `completed` -> `expired`. Also: `uploading` -> `failed`.

**Update rules:**
1. Manifest is append-mostly: chunks move `pending` -> `completed` or `pending` -> `failed`. Never backwards.
2. Atomic updates: each write replaces the full JSON. No partial updates.
3. Client is authoritative during upload: the uploading client updates the manifest after each chunk.
4. Events are bounded: keep only the last 100 events.
5. `file.name` is `null` server-side (filename is in the SGMETA envelope inside the encrypted payload -- zero-knowledge).

**Chunk checksums are computed on encrypted data** (not plaintext). This is safe to store server-side and reveals nothing about the plaintext content.

**Evidence:** Transfer-manifest-schema architecture document, research document 06 (encryption metadata fields).

### AD-6: Compress Before Encrypt (Pipeline Invariant)

**Decision:** The pipeline order is **compress -> encrypt -> upload** for sending and **download -> decrypt -> decompress** for receiving. This invariant is enforced at the engine level, not left to adapter implementations.

**Rationale:** Encrypted data is indistinguishable from random and does not compress. Encrypting before compressing wastes CPU and bandwidth. The engine orchestrator enforces this by calling adapters in the correct order -- compression adapters never see ciphertext, and crypto adapters never see compressed-then-encrypted data.

**Pipeline enforcement in the engine:**

```javascript
// Upload pipeline (engine enforces order)
async upload(data, options) {
    let processedData = data;

    // Step 1: Compress (optional)
    if (this.compression && this.compression.shouldCompress(options.contentType, data.slice(0, 12))) {
        processedData = await this.compression.compress(data);
        const ratio = processedData.byteLength / data.byteLength;
        if (ratio > 0.95) {
            processedData = data; // Not worth compressing
        }
    }

    // Step 2: Chunk
    const chunks = this.chunkManager.split(processedData, this.config.chunkSize);

    // Step 3: Encrypt each chunk (optional)
    // Step 4: Upload each encrypted chunk
    // (Steps 3 and 4 can be pipelined per-chunk)
}
```

**Compression ratio threshold:** If `compressed.byteLength / original.byteLength > 0.95` (less than 5% reduction), skip compression and set `manifest.file.compression = "none"`. This avoids wasting decompression CPU on the download side for negligible savings.

**Evidence:** Research document 05 (compression algorithms), CLAUDE.md pipeline invariant rule.

### AD-7: Pure JavaScript ESM, Zero Platform-Specific Imports in Core

**Decision:** The core engine is pure JavaScript using ESM module format. Zero platform-specific APIs (`fs`, `window`, `Deno`, `process`) in the core engine code. All platform access goes through injected adapters.

**Rationale:** The engine must run identically in browsers, Node.js, Deno, and Bun. Platform-specific code is isolated in adapter implementations. The core engine only uses standard JavaScript APIs: `Promise`, `Uint8Array`, `DataView`, `TextEncoder`, `JSON`, `Map`, `Set`, `AbortController`.

**Module format:** ESM (`"type": "module"` in package.json). All files use `.mjs` extension. No CommonJS.

**Package name:** `@sgraph/transfer-engine` (or `@sgraph-ai/send` as currently configured in package.json).

**Current code state:** The existing `sgraph_ai_send/index.mjs` exports only `{ version }` from `Version.mjs`. `Version.mjs` uses `node:fs` and `node:url` -- this will need to be refactored or moved to an adapter pattern. The core engine will be built in `src/core/` with adapters in `src/adapters/`.

**Evidence:** CLAUDE.md architecture principles, human brief v0.3.2.

### AD-8: Seven Adapter Interfaces (Not Six)

**Decision:** Define seven adapter interfaces, not the six originally proposed. The `ManifestStore` is separated from `StorageAdapter` because manifests have different access patterns (frequent reads/writes, JSON format, different caching/consistency needs) and may live in a different location than chunk data.

**The seven adapters:**

| # | Adapter | Required | Phase 1 Implementations |
|---|---------|:--------:|------------------------|
| 1 | **StorageAdapter** | Yes | `S3StorageAdapter`, `MemoryStorageAdapter` |
| 2 | **TransportAdapter** | Yes | `FetchTransportAdapter` |
| 3 | **ManifestStore** | Yes | `S3ManifestStore`, `MemoryManifestStore` |
| 4 | **CryptoAdapter** | No | `WebCryptoAdapter`, `NullCryptoAdapter` |
| 5 | **CompressionAdapter** | No | `NullCompressionAdapter` (compression deferred from Phase 1) |
| 6 | **CacheAdapter** | No | `MemoryCacheAdapter`, `FilesystemCacheAdapter` |
| 7 | **ProgressAdapter** | No | `ConsoleProgressAdapter`, `CallbackProgressAdapter`, `NullProgressAdapter` |

**Optional adapters default to no-op:** If no `CryptoAdapter` is provided, the engine skips encryption. If no `CompressionAdapter` is provided, the engine skips compression. If no `CacheAdapter` is provided, chunks are not cached locally. If no `ProgressAdapter` is provided, the engine runs silently.

**Required adapters:** `StorageAdapter`, `TransportAdapter`, and `ManifestStore` must always be provided. The engine constructor validates this.

**Evidence:** Adapter-interfaces architecture document.

### AD-9: Retry with Exponential Backoff (tus Pattern)

**Decision:** Implement per-chunk retry with exponential backoff using the tus-js-client backoff array pattern.

**Configuration:**

```javascript
{
    maxRetries:   3,
    retryBackoff: [0, 1000, 3000, 5000], // ms delay before each retry attempt
}
```

**Semantics:** `retryBackoff[0]` = delay before first retry (0 = immediate), `retryBackoff[1]` = delay before second retry, etc. Array length determines maximum retry attempts (4 in this case, plus the original attempt = 5 total).

**Error-to-action mapping:**

| Error Type | Engine Action |
|------------|--------------|
| `NetworkError` | Retry with backoff |
| `HttpError` (429 Too Many Requests) | Retry with extended backoff (2x normal delay) |
| `HttpError` (503 Slow Down from S3) | Retry with backoff + jitter |
| `HttpError` (5xx) | Retry with backoff |
| `HttpError` (4xx except 429) | Fail immediately (no retry) |
| `UrlExpiredError` | Re-request presigned URL from `StorageAdapter`, then retry |
| `AbortError` | Stop (user cancelled via `AbortController`) |
| `AuthenticationError` (GCM tag mismatch) | Fail immediately (data tampered, cannot recover) |
| `CacheQuotaError` | Evict old transfers, retry cache write |

**Jitter for S3 503:** Add `Math.random() * 500` ms to the backoff delay to prevent thundering herd when multiple concurrent uploads hit the same S3 partition.

**Evidence:** Research document 02 (tus retry pattern), research document 04 (S3 503 handling).

### AD-10: Parallel Chunk Upload with Configurable Concurrency

**Decision:** Upload chunks in parallel with a configurable concurrency limit. Default: 4 concurrent chunk uploads.

**Configuration:**

```javascript
{
    maxParallelism: 4,  // Concurrent chunk uploads/downloads
}
```

**Memory impact:** With 4 concurrent uploads at 4 MB chunk size, maximum memory usage is ~32 MB (4 chunks x 2 copies each for plaintext and encrypted data). This is acceptable for all target platforms.

**Implementation pattern:**

```javascript
async function uploadWithConcurrency(chunks, maxParallel) {
    const queue = [...chunks];
    const active = new Set();

    while (queue.length > 0 || active.size > 0) {
        while (queue.length > 0 && active.size < maxParallel) {
            const chunk = queue.shift();
            const promise = uploadChunk(chunk)
                .then(() => active.delete(promise))
                .catch((err) => { active.delete(promise); throw err; });
            active.add(promise);
        }
        if (active.size > 0) {
            await Promise.race(active);
        }
    }
}
```

**Evidence:** Research document 01 (S3 supports parallel part upload), research document 04 (rate limit analysis).

### AD-11: Typed Error Hierarchy

**Decision:** All adapter errors extend a base `TransferError` class. The engine uses error types to decide retry vs. fail vs. abort.

**Error hierarchy:**

```
TransferError (base)
+-- TransportError           -- Network/HTTP failures
|   +-- NetworkError         -- Connection failed, DNS, timeout
|   +-- HttpError            -- Non-2xx response (has statusCode property)
|   +-- AbortError           -- Request cancelled (AbortController)
+-- StorageError             -- Storage backend failures
|   +-- UrlExpiredError      -- Presigned URL expired
|   +-- QuotaExceededError   -- Storage limit reached
|   +-- NotFoundError        -- Object/manifest not found
+-- CryptoError              -- Encryption/decryption failures
|   +-- AuthenticationError  -- GCM tag mismatch (tampered data)
|   +-- KeyError             -- Invalid key format or size
+-- CompressionError         -- Compression/decompression failures
+-- CacheError               -- Local cache failures
|   +-- CacheQuotaError      -- Browser storage quota exceeded
+-- ManifestError            -- Manifest read/write failures
    +-- ManifestConflict     -- Concurrent update detected
```

**All errors carry:**
- `message` (string) -- human-readable description
- `code` (string) -- machine-readable error code (e.g., `TRANSPORT_NETWORK`, `CRYPTO_AUTH_FAILED`)
- `retryable` (boolean) -- whether the engine should retry this operation
- `cause` (Error | undefined) -- the underlying error

**Evidence:** Adapter-interfaces architecture document (Section 11: Error Model).

### AD-12: Checksum on Encrypted Data (SHA-256)

**Decision:** Compute SHA-256 checksums on encrypted chunk data (ciphertext), not on plaintext. Store checksums in the manifest under `chunks.checksums`.

**Rationale:** Checksums on plaintext would leak information about content patterns (identical plaintexts produce identical hashes, enabling deduplication-based attacks on zero-knowledge). Checksums on ciphertext are safe to store server-side because each chunk is encrypted with a unique IV, producing unique ciphertext even for identical plaintext.

**Implementation:**

```javascript
async function checksumChunk(encryptedData) {
    const hash = await crypto.subtle.digest('SHA-256', encryptedData);
    const hex = Array.from(new Uint8Array(hash))
        .map(b => b.toString(16).padStart(2, '0'))
        .join('');
    return `sha256:${hex}`;
}
```

**Verification:** On download, the engine computes the SHA-256 of each downloaded chunk and compares it to the manifest's `chunks.checksums[index]`. A mismatch triggers a re-download of that chunk.

**Evidence:** CLAUDE.md rule 7 ("Chunk checksums on encrypted data -- never on plaintext"), transfer-manifest-schema architecture document.

## 2. Adapter Interfaces to Define

### 2.1 StorageAdapter

Manages the storage backend -- generating upload/download URLs, initiating multipart uploads, completing/aborting them.

```javascript
class StorageAdapter {

    /**
     * Initialize a new chunked upload.
     * For S3: creates a multipart upload and returns the upload ID.
     *
     * @param {string} transferId - 12-char hex transfer identifier
     * @param {object} metadata
     * @param {string} metadata.contentType - MIME type hint
     * @param {number} metadata.totalChunks - Number of chunks
     * @param {number} metadata.totalSize - Total encrypted size in bytes
     * @returns {Promise<{ uploadId: string, prefix: string }>}
     * @throws {StorageError}
     */
    async initUpload(transferId, metadata) {}

    /**
     * Generate a presigned URL for uploading a single chunk.
     *
     * @param {string} transferId
     * @param {string} uploadId - Backend upload session ID (e.g., S3 multipart upload ID)
     * @param {number} chunkIndex - Zero-based chunk index
     * @param {number} chunkSize - Size of this chunk in bytes (encrypted size)
     * @returns {Promise<{ url: string, headers: object, method: string }>}
     * @throws {StorageError | UrlExpiredError}
     */
    async getUploadUrl(transferId, uploadId, chunkIndex, chunkSize) {}

    /**
     * Generate a presigned URL for downloading a single chunk.
     *
     * @param {string} transferId
     * @param {number} chunkIndex - Zero-based chunk index
     * @returns {Promise<{ url: string, headers: object }>}
     * @throws {StorageError | NotFoundError}
     */
    async getDownloadUrl(transferId, chunkIndex) {}

    /**
     * Signal that all chunks are uploaded. Finalize the storage operation.
     * For S3: completes the multipart upload with ETags.
     *
     * @param {string} transferId
     * @param {string} uploadId
     * @param {Array<{ index: number, etag: string }>} parts - Completed parts with ETags
     * @returns {Promise<void>}
     * @throws {StorageError}
     */
    async completeUpload(transferId, uploadId, parts) {}

    /**
     * Abort an in-progress upload. Cleans up backend resources.
     *
     * @param {string} transferId
     * @param {string} uploadId
     * @returns {Promise<void>}
     * @throws {StorageError}
     */
    async abortUpload(transferId, uploadId) {}

    /**
     * Delete all storage artifacts for a transfer.
     *
     * @param {string} transferId
     * @returns {Promise<void>}
     * @throws {StorageError}
     */
    async deleteTransfer(transferId) {}
}
```

**Phase 1 implementations:**
- `S3StorageAdapter` -- uses `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`. Supports AWS S3, R2, B2 via configurable endpoint.
- `MemoryStorageAdapter` -- in-memory `Map<string, Uint8Array>` for tests.

### 2.2 TransportAdapter

Moves bytes between the client and storage URLs. Handles HTTP requests, per-chunk progress, and per-request retry signaling.

```javascript
class TransportAdapter {

     * @param {AbortSignal} [options.signal] - AbortController signal for cancellation
     * @returns {Promise<{ etag: string, statusCode: number }>}

    /**
     * Download a chunk from the given URL.
     *
     * @param {string} url - Presigned download URL
     * @param {object} options

     * @param {function} [options.onProgress] - (bytesDownloaded, totalBytes) => void
     * @param {AbortSignal} [options.signal] - AbortController signal for cancellation
     * @returns {Promise<Uint8Array>}
     * @throws {TransportError}
     */
    async downloadChunk(url, options = {}) {}
}
```

**Phase 1 implementation:**
- `FetchTransportAdapter` -- uses the `fetch()` API (available in browsers, Node.js 18+, Deno, Bun). Configuration: `{ timeout: 30000, retries: 3, retryBackoff: [0, 1000, 3000, 5000] }`. Note: `fetch` does not expose upload progress in browsers -- this is acceptable for Phase 1 (CLI-first). Phase 2 adds `XHRTransportAdapter` for browser upload progress.

### 2.4 CryptoAdapter

Per-chunk encryption and decryption. The engine calls this after compression and before upload.

```javascript
class CryptoAdapter {

    /**
     * Generate a new encryption key for a transfer.
     *
     * @returns {Promise<CryptoKey>} A new AES-256-GCM key (extractable)
     */
    async generateKey() {}

    /**
     * Import a key from raw bytes (e.g., from URL hash).
     *
     * @param {Uint8Array} rawKey - 32 bytes (256 bits)
     * @returns {Promise<CryptoKey>}
     * @throws {KeyError}
     */
    async importKey(rawKey) {}

    /**
     * Export a key to raw bytes (for sharing via URL hash).
     *
     * @param {CryptoKey} key
     * @returns {Promise<Uint8Array>} 32 bytes
     */
    async exportKey(key) {}

    /**
     * Generate a random base IV for a transfer (8 bytes).
     * Combined with chunk index to produce the full 12-byte IV.
     *
     * @returns {Uint8Array} 8 random bytes
     */
    generateBaseIV() {}

    /**
     * Encrypt a single chunk.
     *
     * @param {CryptoKey} key
     * @param {Uint8Array} plaintext - Chunk data (possibly compressed)
     * @param {object} context
     * @param {Uint8Array} context.baseIV - 8-byte per-transfer base IV
```

### 3.4 Transfer ID Generation

Transfer IDs are 12-character hex strings generated from cryptographically secure random bytes.

```javascript
function generateTransferId() {
    const bytes = new Uint8Array(6);  // 6 bytes = 48 bits = 12 hex chars
    globalThis.crypto.getRandomValues(bytes);
    return Array.from(bytes)
        .map(b => b.toString(16).padStart(2, '0'))
        .join('');
}
```

This provides ~281 trillion unique IDs (2^48), with a collision probability of 1 in 16.8 million after 1 million transfers (birthday bound).

## 5. Key Research Findings

### From Research 01 (S3 Multipart and Presigned URLs)

- **Presigned URLs for multipart parts work.** Use `UploadPartCommand` (not `PutObjectCommand`) when generating presigned URLs for parts. `PutObjectCommand` silently ignores `UploadId` and `PartNumber`.
- **CORS is critical.** `ExposeHeaders: ["ETag"]` must be set on the S3 bucket. Without it, JavaScript cannot read the ETag from each part upload response, and `CompleteMultipartUpload` fails.
- **Lambda is never in the data path.** Lambda generates URLs and manages state. File data flows browser -> S3 directly.
- **Transfer Acceleration is compatible** with multipart upload and presigned URLs. Enable via `useAccelerateEndpoint: true` on the S3 client. Phase 1 supports it as a configuration option but does not enable it by default.

### From Research 02 (tus/Uppy Evaluation)

- **Build from scratch is the correct decision.** Scorecard: tus-js-client 2/7, Uppy+tus 2.5/7, Uppy+S3 2.5/7, Resumable.js 1/7, Flow.js 1/7, scratch 7/7.
- **Borrow the retry backoff array pattern** from tus-js-client: `[0, 1000, 3000, 5000]`.
- **Borrow the `httpStack` pluggable transport concept** from tus-js-client.
- **Borrow the S3 multipart function interface** from Uppy's `@uppy/aws-s3`: `createMultipartUpload()`, `signPart()`, `completeMultipartUpload()`.

### From Research 03 (Browser Storage APIs)

- **OPFS is 2-7x faster than IndexedDB** for large binary data. Random-access file operations via `FileSystemSyncAccessHandle` (Web Worker only).
- **Dual-storage pattern:** OPFS for encrypted chunks, IndexedDB for metadata/manifests. IndexedDB fallback when OPFS unavailable.
- **Phase 2 concern:** Browser storage is not needed for Phase 1 (CLI-first). The architecture reserves the `CacheAdapter` slot for browser implementations in Phase 2.

### From Research 04 (S3 Constraints and Costs)

- **Egress is 98-99% of per-transfer cost.** Storage and request costs are negligible for short-lived transfers.
- **Hash-based prefix distribution** (first 2 chars of transfer ID as hex prefix) provides 256 partitions, supporting 896,000 PUT requests/second.
- **Lifecycle policies are critical:** abort incomplete multipart uploads after 1 day; auto-delete completed transfers after 7 days.
- **Dynamic chunk sizing** is necessary for files > ~40 GB to stay under 10,000 parts.

### From Research 05 (Compression Algorithms)

- **CompressionStream API (gzip)** is the zero-dependency default: works in all modern browsers and Node.js, 0 KB bundle cost.
- **fflate (~8 KB)** is the first upgrade: configurable compression level, streaming, all runtimes.
- **Auto-skip detection** is essential: JPEG, PNG, MP4, ZIP, and other already-compressed formats get ~0% compression. Magic bytes + content-type check avoids wasting CPU.
- **Deferred to Phase 2:** Compression adds complexity to the pipeline. Phase 1 ships with `NullCompressionAdapter`. The pipeline slot is reserved.

### From Research 06 (Chunked Encryption Patterns)

- **Counter-derived IVs are recommended** over random IVs. Uniqueness is guaranteed by construction (no birthday bound). Deterministic: same chunk index always produces the same IV.
- **AAD prevents structural attacks:** chunk reordering, deletion, duplication, and cross-transfer replay are all detected via AAD mismatch.
- **Per-chunk overhead is 28 bytes** (12 IV + 16 GCM tag). At 4 MB chunks, this is 0.0007%.
- **Web Crypto API is universal.** `globalThis.crypto.subtle` works in browsers, Node.js 19+, Deno, Bun. One implementation covers all runtimes.
- **AES-256-GCM throughput:** 1-4 GB/s in browsers, 2-6 GB/s in Node.js. Encryption is not the bottleneck.

### From Research 07 (Cloud Providers Comparison)

- **A single S3 adapter covers 4 providers:** AWS S3 + Cloudflare R2 + Backblaze B2 + GCS (S3-compatible XML API). Only Azure requires a separate adapter.
- **R2 is 95x cheaper than S3** for egress ($0.00 vs $0.09/GB). Same S3 API, config change only.
- **Phase 1: AWS S3.** Phase 3+: switch to R2 for cost optimization with an endpoint configuration change.

### From Research 08 (WebRTC P2P Transfer)

- **Phase 3, not Phase 1.** WebRTC adds significant complexity (STUN/TURN, NAT traversal, signaling server).
- **Hybrid architecture:** try WebRTC first, fall back to S3. Both parties must be online simultaneously for P2P.
- **TURN cost:** Cloudflare Realtime at $0.05/GB (cheaper than S3 egress at $0.09/GB).

### From Research 09 (Lambda Streaming Responses)

- **Lambda is not in the data path.** The 6 MB request payload limit is a hard cap. The 200 MB streaming response limit with 2 MB/s throttle is too restrictive.
- **Presigned URLs are the answer** for both upload and download. Lambda handles auth and URL generation only.
- **Lambda streaming is "likely never"** for our use case.

### From Research 10 (Content-Addressable Storage)

- **SHA-256 hash-based chunk keys** enable within-transfer deduplication and resume.
- **Fixed-size 4 MB chunks for Phase 1.** Content-defined chunking (CDC/FastCDC) deferred to Phase 4.
- **CAS is safe with zero-knowledge encryption** because each transfer uses a random key, preventing cross-transfer deduplication (which would leak information about content).
- **Phase 4 concern:** CAS requires additional infrastructure (chunk reference counting, garbage collection). Not needed for Phase 1.
